`capabilities::matrix_markdown` and checked byte for byte by
`crates/bp-platform/tests/platform_matrix.rs` (release plan M2-12). Edit
the code and regenerate; never edit the second table by hand.

The Windows cells for registration, the association lookup, the Settings
link, the console and the crash box are implemented in
`crates/bp-platform-windows` and compile for `x86_64-pc-windows-msvc`; they
have not yet been run on a Windows machine (release plan M0-12 / M2-03).
The deep link's `registeredAppUser` parameter needs Windows 11 21H2 or 22H2
with the 2023-04 cumulative update, or 23H2 and later, per Microsoft's
"Launch the Default Apps settings page"; an older build ignoring it opens
the generic page.

Why, wherever the answer is not a plain yes:

- **`desktop-entry`, Windows**: Windows has no `.desktop` entry; file types are registered under HKCU\Software\Classes instead.
- **`mime-association`, Windows**: Windows associates by file extension, not by MIME type.
- **`windows-file-type-registration`, Windows**: The registry values are generated and can be saved as a `.reg` file for you to run. Applying them is the per-user installer's job, which is not built yet; the application itself never writes the registry (ADR-0032).
- **`windows-file-type-registration`, Linux**: There is no registry on Linux.
- **`default-app-handoff`, Linux**: Linux has no single default-apps settings page to hand the user to; the association is set directly through `xdg-mime`.
- **`association-install`, Windows**: The application never writes the registry (ADR-0032): the per-user installer applies the registration, and a portable copy saves it as a `.reg` file for you to read and run.
- **`association-install`, Linux**: Available unless the product runs as a Flatpak, whose sandbox manages file associations itself; `editor::set_as_default_availability` asks the environment which.
- **`credential-store`, Windows**: Deferred to 1.x (release plan scope S4). The signing key is kept in a passphrase `.bpadx` envelope in the data directory (decision 16), so nothing in 1.0 needs a vault; DPAPI or Secret Service would later wrap that key rather than replace it.
- **`credential-store`, Linux**: Deferred to 1.x (release plan scope S4). The signing key is kept in a passphrase `.bpadx` envelope in the data directory (decision 16), so nothing in 1.0 needs a vault; DPAPI or Secret Service would later wrap that key rather than replace it.
- **`biometric-unlock`, Windows**: Deferred to 1.x with the credential store (release plan scope S4). It is also per-machine: Windows 10 may have no enrolled biometric at all.
- **`biometric-unlock`, Linux**: There is no desktop-wide biometric prompt on Linux to call.
- **`file-permission-narrowing`, Windows**: `std::fs::Permissions` on Windows exposes one bit, the read-only attribute, which controls writing rather than reading. Narrowing the access control list properly is a Win32 call, which `bp-platform-windows` does not make yet. A file's permissions are whatever its directory passed down.
- **`extended-length-paths`, Windows**: Beyond 259 characters a path needs either the `\\?\` prefix -- which `paths::to_extended_length` produces, and which disables every normalisation Win32 usually applies -- or the machine-wide LongPathsEnabled setting together with an application manifest.
- **`case-sensitive-paths`, Windows**: Windows treats `Notes.txt` and `notes.txt` as one file. NTFS can be told otherwise per directory, so this is what to assume rather than what is certainly true of any given folder.
- **`native-clipboard-history`, Windows**: Windows keeps a clipboard history the product could read; doing so is a Win32 call that `bp-platform-windows` does not make yet. The product's own history in `bp-clipboard` works on both platforms in the meantime.
- **`native-clipboard-history`, Linux**: There is no clipboard history in X11 or Wayland to read; what a user has is whatever their clipboard manager kept.
