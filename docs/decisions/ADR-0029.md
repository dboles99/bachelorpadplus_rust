# ADR-0029: Machine-specific state leaves the roaming directory, and is adopted rather than abandoned

**Status:** Accepted
**Date:** 2026-09-25

## Context

Three things the shell writes lived beside `config.toml`: the recent-files
list, the recovery journal and the security history. On Windows that
directory is `%APPDATA%`, which roams -- it is copied to every machine the
user signs into, over a network at sign-out. All three are specific to one
machine: the recent list is absolute paths, the journal is this machine's
unsaved work, and the history is this machine's security events.
`bp_platform::DirKind` already named the right directory for each, and
`DirKind::roams` already warned against this. Nothing used either answer.

Two test-hygiene defects had the same cause. `AppState::new()` resolved
the real directories, so `cargo test` created an empty recovery directory
in the developer's configuration directory on every run and replaced
their recent list with the paths of test fixtures. The security history had
already hit this and been fixed on its own; the other two had not.

## Decision

| What | Where | `DirKind` |
| --- | --- | --- |
| recent files | `%LOCALAPPDATA%\bachelorpad\state\recent.toml`, `$XDG_STATE_HOME/bachelorpad/recent.toml` | `State` |
| security history | `…\state\security-history.log`, `$XDG_STATE_HOME/bachelorpad/security-history.log` | `State` |
| recovery journal | `…\data\recovery\`, `$XDG_DATA_HOME/bachelorpad/recovery/` | `Data` |

**The journal is `Data`, not `State`.** `bp-platform`'s own doc for `Data`
lists the recovery journal by name, and the XDG specification reserves
`$XDG_STATE_HOME` for things "not important or portable enough" for the data
directory. Unsaved work is the most important thing this product writes.
The work queue had filed all three as `State`; that was a shorthand for "not
`Config`", and this is the precise answer.

**An old location is adopted, not abandoned.** At startup,
`bp_config::Locations::for_host` renames each old file or directory to its
new place, whole, with one rename. `bp_config::locations::adopt` carries the
rules:

1. Nothing at the old location: nothing to do.
2. Something at the new location already: use it, and leave the old one
   untouched. An *empty directory* does not count. Merging two journals whose
   file names may collide is not something to do unasked.
3. Otherwise rename. **If the rename fails, keep using the old location** --
   for this session and every one after it until a move succeeds.

Rule 3 is the one that makes moving a journal safe. `%APPDATA%` and
`%LOCALAPPDATA%` are almost always on one volume, and "almost always" is not
a standard for the only copy of someone's typing. A move that cannot happen
costs the user a roaming nuisance; a move that half-happens or is skipped
without notice costs them their work.

Rules 2 and 3 are **reported** in the status bar at startup, with the path.
Both leave something where the product will not look for it on its own.

**Paths are a value handed to `AppState`, not a lookup inside it.** The shell
calls `Locations::for_host()` once; under test, one `cfg(test)` function
builds a unique set of paths under the temp directory instead. That is the
same fix the security history already had, extended to the other two, and
`for_host` -- which may rename things -- is never called by a test.

## Consequences

- The configuration directory holds configuration and nothing else. The
  existing test `the_config_file_is_never_put_in_a_disposable_directory`
  now has a counterpart in `bp-config` asserting that none of the three
  lands in a directory `bp-platform` says roams, on either platform, from
  either leg of CI.
- On Linux nothing roams, so the user-visible change is only that the files
  move from `~/.config` to `~/.local/state` and `~/.local/share`. That is
  what the XDG specification asks for and what backup tools expect.
- `legacy_path_in` stays until nobody can be upgrading from a build that
  wrote beside `config.toml`. Removing it earlier would leave a recovery
  journal behind silently, which is the outcome this ADR exists to prevent.
- Settings still roam, deliberately. So does nothing else.
