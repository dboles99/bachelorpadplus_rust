# ADR-0080: `TextInput` Says Where Its Caret Is, And Six Places Said Otherwise

**Status:** Accepted
**Date:** 2026-09-10
**Amends:** [ADR-0018](ADR-0018.md), [ADR-0048](ADR-0048.md)
**Numbering:** this file is 0080 and not 0057 -- see the last section

## Context

Thirteen menu rows were greyed in the build every user runs: Edit's Duplicate
Line, Move Line Up and Move Line Down; Insert's five date/time stamps; Insert's
Bold, Italic, Link, Code Block and Table. Each needs to know **where the caret
is**, and the reason given was always the same one:

> `TextInput`'s caret is unreadable from here.

That sentence, or a paraphrase of it, was in six places: `menus.rs` twice,
`app.slint`'s `paste-from-clipboard`, `docs/product/MENU_MAP.md`'s definition of
the word **Caret**, `ADR-0018`'s measured "tax" of four features, and the
`dispatch` arms that turned a click into
*"date and time insertion needs --editor-view"*.

**It was never true.** `i-slint-compiler-1.17.1/builtins.slint`, lines
1681-1684:

```slint
// Internal, undocumented property, only exposed for tests.
out property <int> cursor-position_byte-offset;
// Internal, undocumented property, only exposed for tests.
out property <int> anchor-position-byte-offset;
```

Both are real `Property<i32>` fields on the item, set on every caret move
(`i-slint-core-1.17.1/items/text.rs:1617`), and both are readable from an
application's own `.slint`. That was **confirmed by compiling** rather than by
reading: `editor.cursor-position-byte-offset` was added to a function in
`app.slint`, `cargo check -p bp-ui` passed, and the probe was reverted before
anything was built on it.

**This is trap 6 in its most expensive form** -- *a claim in the record is not a
property of the repository* -- crossed with trap 8, *before asking a question,
grep for its answer*. It cost eight sessions and thirteen rows.

### And somebody had already found it

**The answer was not only in the dependency. It was in this repository, in a doc
comment, and had been for some time.** `AppState::cursor_label`, in
`bp-ui/src/state.rs`:

> specs.md section 3 asks for line and column. **Under `TextInput` the caret is
> reachable only through a property marked internal and undocumented**, so the
> honest answer there is the thing we do know.

That is correct, it names the exact obstacle, and the decision built on it --
do not depend on a toolkit internal merely to label a status bar -- is
defensible and stands. **What failed was propagation.** Four other places went
on asserting the caret was *unreadable*:

| Says | Where |
| --- | --- |
| "reachable only through a property marked internal and undocumented" | `state.rs`, `cursor_label` -- **true** |
| "`TextInput`'s caret is unreadable from here" | `menus.rs` |
| "the caret is not readable" | `app.slint` |
| "**Caret** means live only under `--editor-view` … `TextInput` will not say" | `MENU_MAP.md` |
| "only *reading* the caret is impossible under `TextInput`" | ADR-0018 |

***"Reachable only through an internal property"* and *"not reachable"* are not
the same sentence**, and the distance between them is thirteen working menu
rows. The first is a cost to weigh; the second is a wall. Nobody reconciled them
because nothing ever required the two to be read together -- the status bar and
the menu are different files, different features, and different sessions.

**So this is trap 8 pointed at the sharpest case of it yet.** D16 sat for two
sessions while its answer was in `bp-security`'s types; this sat for eight while
its answer was in `bp-ui`'s own prose, one crate away from the code that denied
it. **A decision recorded in a comment is still a decision, and a *local*
decision not to use a capability reads, three files away, as proof the
capability does not exist.**

### And a defect the same seam was hiding

Looking for the caret found the opposite conversion missing. Slint's
`set_selection_offsets` takes **byte** offsets -- `safe_byte_offset` is
`ceil_char_boundary` (`items/text.rs:1835`, `:1347`). `bp_search` produces
**character** indices, deliberately, and says so in its module header:

> Offsets are **character** indices, not bytes, because they are handed
> straight to the editor to select a match.

`dispatch::{select, reveal}` handed that character range to the widget with no
conversion. So **Find highlighted the wrong span in the default editor surface
on any document with a multi-byte character before the match** -- and never
said so, because the offset is clamped to a character boundary rather than
refused. `"héllo cat"`: "cat" is characters 6..9 and bytes 7..10; asking for
6..9 as bytes selects from the `l`.

Every test of Find in this repository used ASCII, where the two numbers are
equal. `tests/integration/tests/search_over_buffer.rs` existed precisely to
test this seam across three crates and its own header names the symptom --
*"a find that highlights the wrong text"* -- but the fourth participant, the
shell, was not in it.

## Decision

### 1. The conversion lives in a library, once

`bp_buffer::Buffer` gains `char_of_byte` and `byte_of_char`, over `ropey`'s
`byte_to_char`/`char_to_byte`, both clamping rather than panicking because both
are reached from UI code. A byte interior to a character rounds **down**, which
is the only answer that keeps a caret inside the document it was reported from.

**No allocation of the document.** The rope answers directly, so this does not
go near R011's trap 5 -- unlike anything built on `active_text()`.

`bp_editor::Editor` gains `set_cursor_at_byte`, `select_bytes` and
`bytes_of_chars`. They route through the existing `set_cursor`/`select`, so they
inherit `caret_position`'s rule about not landing between a `\r` and its `\n` --
a caller doing its own arithmetic would have to remember that, and would
eventually not.

### 2. The thirteen rows are live in both surfaces

**And the guard behind them comes out too, which this ADR got wrong once
before getting it right.** `AppState::run_line_edit` began with
`if !self.editor_view { return; }`. Enabling the three Edit rows without
removing it made each **an enabled row that silently did nothing** -- strictly
worse than the greyed row it replaced, and the precise failure `menus.rs`'s own
convention exists to prevent: *a label that swallows a click reads as broken*.

**The full suite stayed green while that was true**, because
`duplicate_and_move_line_do_nothing_outside_the_custom_editor_view` was still
there asserting it was correct. **Trap 4 from the inside**, and worth recording
against this ADR rather than tidying away: inverting the *menu* tests while
leaving the *state* test is exactly how two claims about one function get out of
step, and 1,997 passing tests did not notice. It was caught by reading the test
names in a run that was investigating something else entirely.

`menus::insert` and `menus::edit` **lose the `editor_view` parameter
altogether**, rather than being passed `true`. A parameter that can only have
one meaning is a place for the old meaning to come back.

`dispatch::adopt_widget_caret` reads the two properties before an edit at the
caret; `hand_caret_back` puts the widget's caret where the rope's caret ended
up. **The second runs after `refresh`, never before**: `PushText::Yes` replaces
the widget's whole text, and a selection set before that push addresses the
document as it was.

The anchor makes the trip with the caret. A construct inserted over a selection
replaces it, and an anchor left behind turns that replacement into an insertion
somewhere else.

### 3. Find is fixed at the same seam

`dispatch::toolkit_offsets` converts a character range to byte offsets in the
two places -- `select` and `reveal` -- that hand one to the widget. A document
with no `Editor` has no rope to convert against; those are served from disk and
never reach here (the viewer owns finding in a huge document,
[ADR-0042](ADR-0042.md)), so that case falls back to the character range and
behaves exactly as it did.

### 4. The guard for an undocumented dependency is the build

Trap 3, turned on this change rather than on somebody else's: **what fails if
`cursor-position-byte-offset` stops being true?**

`.slint` stops compiling. An `out` property that ceases to exist is a **compile
error in `app.slint`**, not a silent zero, so a Slint upgrade that removes it
fails the gate's first stage rather than quietly returning every caret to
position 0. That is the guard, it is recorded here, and it is why there is no
test pretending to check a toolkit internal.

What *is* tested is our own conversion, in `bp-buffer`, where it can be tested
without a window: five cases -- ASCII, a two-byte character, a four-byte
character, a byte interior to a character rounding down, and past-the-end
clamping.

**The Find regression test was watched failing before it was called done.**
`bytes_of_chars` was temporarily reverted to return its input; the test failed
with `left: 6..9, right: 7..10`, which is the defect exactly. A guard nobody has
seen fail is a guard nobody knows the shape of.

## Confirmed at the keyboard, 2026-09-10

**Both halves were driven in the real window, in the default build**, because
this change lives in the one seam no test in this repository can reach -- what
the toolkit does with what it is handed, where five defects have lived.

| Driven | Result |
| --- | --- |
| `{DOWN}`, `^d`, `^s` on `alpha/bravo/charlie` | **`alpha/bravo/bravo/charlie` on disk.** The caret was read at click time and line *two* was duplicated -- so `adopt_widget_caret` sees the widget's caret even though a `MenuPopup`-driven shortcut fires through the same `dispatch`, and `run_line_edit` acts with the guard gone |
| `^f`, `cat` over `héllo cat` | **The highlight sits on `cat`**, counter `1 of 1`. Before the fix, character offsets 6..9 handed to a byte-indexed widget highlighted `lo ` |

Asserted on the **saved bytes** rather than on a screenshot wherever possible:
a capture shows what was drawn, and the file shows what happened.

### And the run that nearly recorded the opposite

**The first two attempts drove an eighteen-day-old binary**, because
`Drive-Window.ps1` checked that `target/release/bachelorpad.exe` *existed* and
never that it was current. They reproduced the *old* behaviour exactly --
nothing in the default surface, correct under `--editor-view` -- which is
indistinguishable from a broken fix, and the captures agreed. `ls` on the
executable is what disproved it.

The script now refuses when the binary is older than the newest `.rs` or
`.slint`, and **the guard was watched failing before it was called done**. The
lesson is in `DECISIONS.md`: **a verification tool that silently measures the
wrong artefact is worse than no verification**, because absent fails loudly and
stale fails convincingly.

## Consequences

**ADR-0018's tax is not four features. It may be zero**, and that ADR's second
re-ask condition -- *"revisit when the tax becomes visible"* -- is met from a
direction it did not anticipate. What `--editor-view` still **costs** is
unchanged and was checked in Slint's source rather than assumed: `FocusScope`
rejects `UpdateComposition` and `CommitComposition` in both handlers, so **CJK
input does not work in that surface**.

So the flag now buys little and still costs that. **Whether it survives is
`D21`** in `project/DECISIONS_NEEDED.md`, and it is deliberately not decided
here: this ADR records what was found, and retiring an editing surface is a
larger decision than the finding that made it askable.

**`EditorSurface` and `--editor-view` are not the same thing**, and nothing here
proposes deleting the surface. It draws every huge document in every build
([ADR-0030](ADR-0030.md)); the flag is a statement about which surface *edits*.

**Six sentences in the record were false and are corrected**, in
`docs/product/MENU_MAP.md`, `ADR-0018`, `menus.rs`, `app.slint` and two
`dispatch` arms. The word **Caret** in `MENU_MAP.md`'s legend no longer names a
category with anything in it.

**The lesson, for `DECISIONS.md`:** *a constraint attributed to a dependency
deserves the same scepticism as a constraint attributed to the record, and it is
cheaper to check.* `cargo check` answered in fifty-five seconds a question that
had shaped four ADRs and thirteen menu rows across eight sessions. ADR-0018 did
check Slint's source -- for **composition**, and found a real refusal there --
and the caret claim rode along beside a verified one without ever being tested
itself. **A true sentence next to an unverified one lends it credibility it has
not earned.**

## Why this file is 0080

The last ADR in this repository is 0056. **0057 through 0079 are deliberately
unused.**

`bachelorpluslite`, derived from this repository at `3589205`, has its own
ADR-0057 through ADR-0076 for entirely different decisions, and this project's
records now link to several of them by number
([project/V1_1_1_PLAN.md](../../project/V1_1_1_PLAN.md) §0b). Two different
ADR-0057s in two repositories that cross-refer is an ambiguity no reader can
resolve from a link, so this sequence skips past theirs with room to spare.

**The gap is the decision, not an accident**, which is why it is recorded in the
first ADR on the far side of it rather than left for somebody to notice.
