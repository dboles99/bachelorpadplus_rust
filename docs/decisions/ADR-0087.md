# ADR-0087: Read-Only Is The Save Refusing

**Status:** Accepted
**Date:** 2026-10-28
**Closes:** `project/WORK_QUEUE.md`'s R1
**Adopted from:** [bachelorpluslite ADR-0066](../../bachelorpluslite/docs/decisions/ADR-0066.md)

## Context

R1 was queued as *"`--readonly`, or rather what it should be instead"* -- a
design pass asking whether the huge-document viewer, Security ▸ Lock
Document, and a read-only buffer property are the same thing.

The answer: **read-only is the save refusing, and the refusal now knows.**

The downstream repository answered this in ADR-0066 after discovering that
`bp_buffer::Access` had no producers -- it was never set by anything, so the
guards in `insert` and `remove` never fired. Read-only was always enforced
at save time by the filesystem refusing the write.

## Decision

**Read-only is not a buffer property; it is a save-time refusal with a
clear message.**

### 1. Add a specific error for read-only files

A new `SaveError::ReadOnlyFile` variant with a message that:
- Names the problem: "the file is marked read-only"
- Offers the solution: "Use Save As to write a copy somewhere else, or
  clear the read-only attribute and try again"

This replaces the generic "it may be read-only" hedge in `SaveError::Replace`
with a definitive answer when we can determine the cause.

### 2. Check the target file's permissions on the failure path

When a replace operation fails, check if the target file is marked
read-only **at that moment** (not remembered from when the file was
opened). This is important because:
- The file's permissions can change while the document is open
- A remembered answer from open time would be wrong

The check is only performed on the error path, so ordinary saves pay
nothing for it.

### 3. On Unix, distinguish between "no write permission" and "read-only attribute"

On Unix, `Permissions::readonly()` checks for the absence of the write bit
for the owner. However, a file owned by someone else with mode 644 will
still refuse writes to us, even though `readonly()` returns false. That
case continues to use `SaveError::Replace` with its hedge, because the hedge
is accurate there.

## Consequences

**More honest error messages.** A user trying to save a read-only file
now gets a clear message about what is wrong and how to fix it, rather
than a guess.

**No change to the buffer.** The `bp_buffer::Buffer` struct keeps its
`access` field and related methods in this repository, because this
repository still has the large-file engine which uses `Access` for
`ReadOnlyBySize`. The downstream removed large-file mode (ADR-0063) and
then discovered `Access` was unused (ADR-0066). Here, `Access` is still
used for large files.

**Back-port of a decision rather than code.** The decision in ADR-0066
that "read-only is the save refusing" applies regardless of whether
large-file mode exists. The specific implementation (deleting `Access`
from `Buffer`) only applies to repositories without large-file mode.

## The lesson

> **A type with no producer is not an implementation. It is a claim.**

Or, more positively: **an error message should be as specific as the
information available.** When we can determine that a file is read-only,
we should say so explicitly rather than listing it as one of several
possibilities.
