# ADR-0014: Work Model and Traceability

**Status:** Accepted
**Date:** 2026-08-16
**Amended:** 2026-09-25 (where tasks and their acceptance criteria live now)

## Context

The project is built largely through AI coding agents working from reusable
prompt packets. That makes provenance -- which prompt produced which artefact
under which task -- worth capturing, and easy to lose if it is not captured
deliberately.

## Decision

Use the hierarchy:

```text
project -> task -> step -> prompts/rosettas -> artifacts -> metadata
        -> database -> note
```

Apply layers only where they add traceability. A task is a bounded objective
with explicit acceptance criteria; a step is a testable action.

## Consequences

- Not every task needs every layer, and forcing them produces ceremony rather
  than traceability.
- A task file without acceptance criteria is incomplete, because the layer
  that makes a task checkable is exactly the one it omitted.
- Generated artefacts record metadata (hash, source task, rosetta) so a file
  under `artifacts/` can be traced back to what produced it.

## Amendment (2026-09-25)

Practice moved away from one file per task, and this records where each
layer actually lives rather than leaving the Consequences above to be read
as describing the repository.

- **Tasks.** `project/RELEASE_PLAN.md` is the task list. Each item names its
  files, size and dependencies, and its **Verify** column names the test,
  gate stage or measurement that proves it done. That column is the
  acceptance criteria this ADR requires; the rule that a task without them is
  incomplete stands, and applies to plan items.
- **`project/tasks/`** keeps one README per folder, with that folder's status
  and the plan items or ADRs its remaining work went to, plus the six phase-1
  and phase-2 task files that were written with real acceptance criteria.
  The other 52 were the scaffold's template with the name changed and no
  criteria; they were deleted by release-plan item M2-13 rather than filled
  in, because filling them in would have copied the Verify column into a
  second place to drift.
- **Artefact metadata.** Not honoured as written. `scripts/New-ArtifactMetadata.ps1`
  writes a record into `metadata/`, but no record has been committed; the
  benchmark JSON under `artifacts/benchmarks/` carries its own time, host and
  compiler instead. The scaffold's `metadata/repository_manifest.json`, a
  file listing with hashes from 2026-08-16 that nothing generated or read,
  was deleted rather than regenerated. Release-plan item M4-04 is the next
  planned user of the script, for per-OS test evidence.
- **Database.** The governance database this hierarchy names exists only as
  the schema in `database/`, which nothing reads (`database/README.md`). The
  product's own metadata store, `bp-storage` (ADR-0019), is a different
  thing.
