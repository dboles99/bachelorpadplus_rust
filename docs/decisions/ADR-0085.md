# ADR-0085: Warn when recovery journal would write secrets in plaintext

## Status

Accepted — implemented 2026-09-11.

## Context

The recovery journal writes the unsaved text of every dirty document to disk
so that work survives a crash. Under the Standard profile this journal is
plaintext, and that is the documented behaviour (ADR-0020).

A document that contains credentials — an API key, a token, a password in a
connection string — can therefore sit on disk in cleartext beside the editor
without the user knowing. This was discovered in the wild on 2026-09-10: a stray
journal file on the development machine held two API-key-shaped strings beside
the service names they belonged to, for six days.

`bp-secrets::scan` (ADR-0011 §15) already exists to find credentials in
document text. Nothing connected the two: a buffer the scanner would flag
was journalled in cleartext anyway, and the user was never told.

## Decision

**Warn the user once per session when a plaintext recovery journal is about
to receive a document that looks like it contains a credential.**

More precisely: when `checkpoint_all` is invoked and a document is dirty,
scan its text. If `bp_secrets::scan` returns any finding with at least
`Confidence::Medium` and the document's recovery policy is
`Recovery::Plaintext`, set a one-shot warning in the status bar:

> this document contains what looks like a credential and is being written
> to the recovery journal in plaintext; encrypt the document to silence
> this warning

The warning fires only once per session (`secrets_warning_shown` flag),
so it does not spam on every keystroke.

## Alternatives considered

| Option | Pros | Cons |
| --- | --- | --- |
| **Warn once** (chosen) | Actionable; user learns the situation and can fix it (encrypt the document) | A determined user can ignore it |
| Refuse to journal | Prevents the leak completely | Breaks the recovery promise for Standard-profile users with secret-looking but innocent text (false positives do happen) |
| Seal regardless of profile | Keeps secrets off disk | **Changes what a profile promises**: Standard explicitly says the journal is plaintext; silently overriding it is worse than the leak |
| Warn on every checkpoint | Keeps the user aware | Spams the status bar; the user will disable it or ignore it within minutes |

## Consequences

- A false positive is still possible, but a false positive once is tolerable;
a false positive every keystroke is not (see above).
- The warning is a nudge, not a blocker. It is the cheapest fix that preserves
the existing guarantees: Standard users who do not care about secrecy keep
their recovery; Confidential users get an encrypted journal already (ADR-0020),
so they never trigger this warning.
- The scan is cheap — linear in the document length — and only runs on dirty
documents during checkpoint, not on every keystroke.

## Rationale

This is the minimum viable reaction to a real finding: a leak happened.

Doing nothing means the next person with a token in their notes will
discover it the same way — in a shell, six days later. Refusing to journal or
sealing regardless of profile would both break the documented contract with
Standard-profile users. Warning once teaches without punishing.
