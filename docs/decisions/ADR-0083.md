# ADR-0083: Wire `Buffer::access` to File Permissions

## Status

Accepted — 2026-09-11

## Context

`Buffer::access` controls whether a buffer accepts edits, and it was observed that
`set_access` and `with_access` had **zero callers** outside `bp-buffer` itself
(WORK_QUEUE.md item C1, 2026-09-10). This meant the read-only guards in
`Buffer::insert` and `Buffer::remove` had never fired, despite being tested.

Two producers of `Access` already existed in the codebase:

1. `LargeFile::open` computes an `Access` from file size and permissions
   (for huge files served from disk)
2. Security ▸ Lock Document forgets a document's passphrase, making it
   read-only from the user's perspective

The downstream repository (`bachelorpluslite`) deleted the type entirely
(ADR-0066 there) because Lite has neither a huge-document viewer nor Lock
Document. **This product has both**, so the same finding argues for wiring
rather than deletion: the capability exists, and we have use cases for it.

Additionally, a third producer was missing: regular files opened through
`bp-files::load` were not setting `Buffer::access` based on file permissions,
so a file read-only on disk would still accept edits and only fail at save time.

## Decision

Wire `Buffer::access` to file permissions and size for all document types:

1. Extend `bp_files::LoadedFile` with a `file_is_read_only` field
2. Capture file metadata in `bp_files::load` and set the field
3. Add `Editor::buffer_mut()` to allow setting the buffer's access after
   construction
4. In `bp-ui::state`, set the editor's buffer access when opening or reloading
   a file using `Access::of(file.bytes_on_disk, file.file_is_read_only)`
5. Set `Access::Editable` for new documents, restored checkpoints, and
   unlocked encrypted documents

This makes the read-only guards active for regular files, matching the
behaviour already present for huge files in the viewer.

## Consequences

**Positive:**

- Read-only files now refuse edits at the rope level, not at the save dialog
- The status bar can truthfully report "Read-only: the file cannot be written"
  for files that are read-only on disk
- Consistency: regular files, huge files, and encrypted files all use the same
  `Access` mechanism
- The read-only guards in `Buffer::insert`/`remove` now fire as intended

**Negative:**

- A file opened read-only on disk that the user wants to edit requires Save As
  rather than simply editing and saving over it — which is the intended
  behaviour and matches other editors
- No change to Lock Document: it remains about passphrase management for
  encrypted documents. A separate "Read-Only Mode" toggle could be added later
  if needed, but is not part of this decision.

**Neutral:**

- The file lock check happens at open time, not continuously. A file that
  becomes read-only while open will still accept edits until the next reload
  or reopen. This is deliberate: checking permissions on every keystroke would
  add overhead and a race condition (the file could change between the
  check and the edit). The current behaviour matches common editors.

## Alternatives Considered

1. **Delete `Buffer::access` entirely** — Rejected because this product has
   use cases (huge files, read-only files) that Lite does not
2. **Make Lock Document set `Buffer::access`** — Rejected for now because Lock
   Document is about passphrase management, not general read-only. If a
   general read-only toggle is added, it should use this mechanism.
3. **Check permissions on every edit** — Rejected due to overhead and race
   conditions. Open-time check is sufficient and matches common practice.
