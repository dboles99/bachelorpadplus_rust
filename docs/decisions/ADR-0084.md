# ADR-0084: Status Bar Reports Line and Column in Both Editor Surfaces

## Status

Accepted — 2026-09-11

## Context

ADR-0080 confirmed that `TextInput`'s caret is readable via `cursor-position-byte-offset`
and `anchor-position-byte-offset`, contradicting six places in the codebase that
claimed it was unreadable. Those thirteen menu rows that were greyed for that
reason went live with ADR-0080.

However, the status bar still only reported line count for TextInput (the
default surface), while showing "Ln X, Col Y" for `EditorSurface` (the
`--editor-view` surface). The reason was written into `cursor_label()`:

> a status bar refreshed on every keystroke is a different risk profile and
> wants its own decision

But ADR-0080 removed that risk: the caret *is* readable, and it is read on
every refresh anyway for other purposes (e.g., `adopt_widget_caret`). The
only thing missing was wiring the byte offset into the status bar label.

## Decision

Extend `cursor_label()` to report "Ln X, Col Y" for both editor surfaces:

1. Add `caret_byte_offset` field to `AppState` to hold the TextInput caret
   position
2. In the `refresh` function, capture `ui.get_caret_byte_offset()` when
   `!editor_view`
3. In `cursor_label()`, for TextInput: convert the byte offset to a character
   position using the buffer's methods, then format as "Ln X, Col Y"
4. For `EditorSurface`: continue using `editor.position()` as before

## Consequences

**Positive:**

- Status bar now shows consistent line/column information in both surfaces
- Users get the same information regardless of which surface they use
- Matches user expectation and common editor behaviour

**Negative:**

- None identified. The conversion is cheap (one byte-to-char lookup) and
  happens on every refresh already for other purposes.

**Neutral:**

- The byte offset capture happens on every refresh for TextInput. This is
  consistent with how the custom surface already works (it reads the caret
  from the editor on every refresh).

## Alternatives Considered

1. **Keep the line count only for TextInput** — Rejected. Users expect
   consistent behaviour, and the technical barrier no longer exists.
2. **Make it opt-in** — Rejected. This is core editor information, not an
   experimental feature.
