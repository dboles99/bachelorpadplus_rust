# ADR-0033: `bp-platform-windows` is the one crate allowed to call Win32

**Status:** Accepted
**Date:** 2026-09-25

## Context

The release needs a handful of Win32 calls that nothing in the standard
library offers: `AttachConsole` so `--version` prints under the GUI
subsystem, `MessageBoxW` for a crash that happens before any window exists,
`SHChangeNotify` after registration, `ShellExecuteW` for the `ms-settings:`
deep link, and a read of `UserChoice` for the association report.
`bp-platform` is deliberately dependency-free and `forbid(unsafe_code)`, and
so is the binary. specs.md §20 already names a `bp-platform-windows` crate;
DECISIONS.md recorded not creating it as a decision until something
genuinely Windows-specific had to be linked. That is now true.

## Decision

- A new crate, `crates/bp-platform-windows`, depends on `windows-sys` and is
  **the only crate in the workspace allowed `unsafe`**. Each unsafe block
  wraps one Win32 call, carries a `// SAFETY:` comment, and is exposed
  through a safe function.
- Everything else stays `#![forbid(unsafe_code)]`, including `bp-platform`
  and `apps/bachelorpad`.
- The crate compiles on every OS; its functions are `cfg(windows)` inside
  and no-ops or `None` elsewhere, so the Linux leg still builds the
  workspace.

## Consequences

- ADR-0001's warning about `cfg`-gated code applies: only the Windows leg of
  the gate exercises the bodies. Each function is kept small enough to read
  whole, and the Windows gate runs at every milestone end.
- `windows-sys` is a new dependency, added in the same change that first
  uses it.

## Implemented

2026-09-25, release plan M2-03. `crates/bp-platform-windows`, on
`windows-sys` 0.61 with only `Win32_Foundation`, `Win32_System_Console`,
`Win32_System_Registry`, `Win32_UI_Shell` and
`Win32_UI_WindowsAndMessaging` enabled, and only under `cfg(windows)`:

- `attach_parent_console()` -- `AttachConsole(ATTACH_PARENT_PROCESS)`, for
  `--version`/`--help` in a GUI-subsystem release build.
- `standard_error_is_connected()` -- `GetStdHandle(STD_ERROR_HANDLE)`, so the
  crash hook shows a box only when nobody is reading stderr.
- `show_fatal_message(title, body)` -- `MessageBoxW` (`MB_OK |
  MB_ICONERROR | MB_SETFOREGROUND`), for that crash.
- `notify_associations_changed()` -- `SHChangeNotify(SHCNE_ASSOCCHANGED,
  SHCNF_IDLIST, null, null)`.
- `open_uri(uri)` -- `ShellExecuteW("open")`, refusing anything that is not
  an `ms-settings:` URI.
- `user_choice_prog_id(ext)`, `class_default_prog_id(ext)`,
  `registered_application(name)`, `windows_build()` -- `RegGetValueW`,
  reads only (ADR-0032); `RegistryProgIds` implements
  `bp_platform::editor::ProgIdQuery` over the first two.

Every `unsafe` block is in the private `sys` module, wraps one call
(`clippy::multiple_unsafe_ops_per_block` denied) and carries a `SAFETY:`
comment (`clippy::undocumented_unsafe_blocks` denied); strings reach Win32
only as a `WideString`, whose constructors guarantee the NUL terminator.
`bp-platform` does not depend on this crate; this crate depends on
`bp-platform` for the trait. `apps/bachelorpad` calls the console and
message-box functions and stays `forbid(unsafe_code)`.

Verified on Linux only: the pure tests run there, and `cargo clippy
--target x86_64-pc-windows-msvc --all-targets -- -D warnings` compiles the
Windows bodies and their tests against `windows-sys`. Nothing has been run on
Windows yet; the Windows gate (M0-12) is the first run.
