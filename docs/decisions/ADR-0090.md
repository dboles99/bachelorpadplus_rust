# ADR-0090: No Installer

**Status:** Accepted
**Date:** 2026-10-29
**Closes:** `project/WORK_QUEUE.md`'s P5
**Adopted from:** [bachelorpluslite ADR-0067](../../bachelorpluslite/docs/decisions/ADR-0067.md)

## Context

P5 was queued as *"An installer, or a decision that there is not one"* with
the note: **"A zip that unpacks anywhere is a defensible answer for this
product; so is MSI or winget. A decision before an estimate."**

Before sizing this work, the inventory found that the downstream repository
(`bachelorpluslite`) had already answered this question in
[ADR-0067](../../bachelorpluslite/docs/decisions/ADR-0067.md).

The key findings from that ADR:
- An installer is the usual mechanism for registering a file type, creating
  start menu entries, and placing an icon in the system theme
- An unsigned installer carries the same trust problem as an unsigned binary:
  it teaches the user to override a security warning for a text editor
- A signed installer would require a code-signing certificate, which
  [ADR-0055](../docs/decisions/ADR-0055.md) deferred to avoid teaching users
  to install root certificates

## Decision

**Ship as a zip archive only. No installer.**

The product is distributed as:
- A Windows zip archive containing the executable, the PNG and ICO icons
  ([ADR-0086](../docs/decisions/ADR-0086.md)), the `.desktop` file, and a
  readme
- A Linux tar.gz archive containing the executable, the PNG icon, and the
  `.desktop` file

Users extract the archive and run the executable directly. On Windows, they
may create a shortcut manually; on Linux, they may place the `.desktop` file
in `~/.local/share/applications/` for menu integration.

### Why no installer is the right answer

1. **Unsigned installers are worse than unsigned binaries.** A user that
   installs an unsigned installer has overridden a security warning for
   software that then runs with elevated privileges (to write to Program
   Files, register file types, etc.). An unsigned binary only warns once
   and then runs with normal privileges.

2. **Signed installers require a certificate.** ADR-0055 deferred buying a
   code-signing certificate. Without one, a signed installer is not
   possible, and an unsigned installer violates the principle above.

3. **Portability.** A zip archive works the same on every platform and in
   every environment. An installer is platform-specific and often
   environment-specific (per-user vs per-machine).

4. **Simplicity.** One archive, one extraction step, no registry changes,
   no admin privileges required. This aligns with the product's philosophy
   of being a simple, portable text editor.

## Consequences

**Release scripts** (`scripts/New-Release.ps1` and `scripts/release-linux.sh`)
produce zip (Windows) and tar.gz (Linux) archives. They do not produce MSI,
winget, deb, rpm, or any other installer format.

**File type registration** on Windows is left to the user via the `.reg`
handoff already shipped ([ADR-0034](../docs/decisions/ADR-0034.md)). The
readme explains how to use it.

**Menu integration** on Linux is left to the user via the `.desktop` file.
Placing it in `~/.local/share/applications/` integrates it with most desktop
environments.

**Icon integration** on both platforms is handled by [ADR-0086](../docs/decisions/ADR-0086.md):
the icon ships beside the executable, and the `.desktop` file references it.

## The lesson

> **A derived repository is a second reader of every decision this one made,
> and it re-checks premises for free.**

This ADR is directly adopted from the downstream repository's ADR-0067,
which answered a question this repository was still carrying. The downstream
repository's decisions are recorded decisions for this one too, and should
be checked before sizing work.
