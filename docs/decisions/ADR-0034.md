# ADR-0034: Nothing leaves the machine in v1

**Status:** Accepted
**Date:** 2026-09-26
**Decision:** release plan decision 17, option (a); D1 in `project/DECISIONS_NEEDED.md`

## Context

Every security profile carries a `network` axis (`bp_security::Network`),
and the Security menu reads it out as "Leaves this machine". Standard and
Private say `Allowed`; Confidential and Maximum say `Denied`. Until now
nothing defined what `Allowed` promised, and the readout said "permitted" --
which reads as though the product sends something somewhere when a looser
profile lets it. It does not: there is no network code in the product.
specs.md names features that would send text off the machine (cloud
embeddings, semantic search against a service), and ADR-0030 defers all of
them past RC1.

## Decision

- **Version 1 sends nothing off the machine.** No crate in the shipped
  binary opens a socket or makes a request. The file dialogs are the
  operating system's (through the desktop portal on Linux), and what they
  do is the operating system's business, not a channel of ours.
- **`Network::Allowed` means "not forbidden, and no consumer exists".** It
  is a constraint a future feature will have to honour, not a permission
  anything uses today. `Network::Denied` is the same constraint made
  explicit, and it will bind the first feature that wants the network.
- The Security menu says so in the user's terms:
  "Leaves this machine: nothing (no network code)" under a profile that
  would allow it, and "Leaves this machine: never (forbidden by this
  profile)" under one that forbids it.
- `SECURITY.md` states it as a property of the release.

## Consequences

- The readout stops implying a capability the product does not have.
- The first networked feature (1.x at the earliest) needs its own ADR, which
  must say what leaves, to where, under which profiles, and how the user
  consents; it must also change the readout, which a menus test pins.
- A dependency that starts making requests on its own would break this ADR
  silently. `cargo deny` (release plan M1-14) bans nothing network-specific
  yet; reviewing new dependencies for it is part of the release checklist.
